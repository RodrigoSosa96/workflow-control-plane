# Control Plane Hardening Roadmap

**Creado:** 2026-07-29 · **Fuente:** review multi-agente profunda — evidencia completa con `archivo:línea` en [`docs/superpowers/reviews/2026-07-29-multi-agent-deep-review.md`](docs/superpowers/reviews/2026-07-29-multi-agent-deep-review.md). Los IDs `D1`–`D18` referencian los hallazgos de esa review. Los patrones atribuidos a oh-my-pi salen del checkout read-only en `~/projects/references/oh-my-pi` (ver `AGENTS.md`, "Reference material").

**Cómo usar este documento:** cada ítem es una unidad de trabajo pequeña (idealmente un commit/PR). Marcá el checkbox al completar y anotá el commit al lado (`- [x] 0.1 … (abc1234)`). Los ítems de Fase 0 son fixes directos: no necesitan diseño previo, sí tests. Los de Fases 1–4 no triviales siguen el flujo normal del repo (brainstorm → spec en `docs/superpowers/specs/` → plan en `docs/superpowers/plans/` → implementación). Dentro de cada batch el orden es el recomendado; entre batches no hay dependencia salvo que se indique.

## Fase 0 — Confiabilidad: quick wins (fixes de líneas, no de días)

Son las fallas *silenciosas* en el camino crítico de estado y notificaciones. Prioridad máxima.

### Batch A — Watchers y pipeline de notificaciones (D2, D3, D12)

- [x] **0.1** Agregar `.catch()` a los schedule de ambos watchers (`worker-watcher.js:74-76`, `delegation-watcher.js:104-106`): registrar el error de forma acotada y seguir polleando. Hoy cualquier error de poll es un unhandled rejection que puede matar el proceso host del coordinador Pi. *(9eebba2)*
- [x] **0.2** Delegation watcher: entregar antes de consumir, o marcar `delivery-failed` redeliverable si `deliverResult` lanza tras `consumeResult` (`delegation-watcher.js:128-140`). Hoy un fallo de entrega pierde el resultado advisory para siempre. *(9eebba2)*
- [x] **0.3** `run-store.list()`: skip por entrada con warning acotado en vez de propagar el throw (`run-store.js:711-721`). Un run dir sin `run.json` (ventana de crash en `create()`, `:619-632`) hoy envenena el listing de todos los runs y cascadea a los watchers. Mantener `read()`/`update()` estrictos. *(9eebba2)*
- [x] **0.4** Corregir `TERMINAL_RUN_STATES` en `worker-watcher.js:3`: usa `needs_input`/`manual_handoff_required` con guion bajo pero los estados reales llevan guion (`run-state.js:8,13`) — esas notificaciones nunca matchean. *(9eebba2)*
- [x] **0.5** Dedupe del worker-watcher por `(runId, generation)` en vez de runId-para-siempre (`worker-watcher.js:106-108`), espejando el `noticeKey` del delegation watcher. Hoy un run que paró, se resumió y completó no re-notifica. *(9eebba2)*
- [x] **0.6** `events-bus.readEvents`: avanzar el cursor solo hasta el último `\n` (`events-bus.js:47-58`). Hoy una línea cortada a mitad de escritura se salta para siempre. *(9eebba2)*
- [x] **0.7** `handoff.js:539`: spread de `process.env` en el env del notifier. Hoy `WORKFLOW_HANDOFF_NOTIFIER` (y `HOME`) se ignoran justo en el path de handoff. *(9eebba2)*

### Batch B — Correctitud de la máquina de estados (D4, D6, D7)

- [x] **0.8** Write final del launcher consciente del estado: en el updater, transicionar a RUNNING solo desde PLANNED/LAUNCHING y estampar FAILED solo desde LAUNCHING; devolver `{}` si el worker ya avanzó (`launch.js:734-743`, `:549-551`). Hoy puede regresar COMPLETED→RUNNING o marcar FAILED a un worker vivo. *(ffc6929)*
- [x] **0.9** Retry acotado (3 intentos, backoff 25–100ms con jitter) en `acquireLock` solo para contención (`run-store.js:446-460`). Hoy una colisión de milisegundos entre el launcher y el hook `onStop` del worker pierde la transición COMPLETED sin diagnóstico. *(ffc6929)* **Actualización (2026-08-03):** ese retry de 3 intentos fue reemplazado por un presupuesto de tiempo compartido de 2000 ms (`bounded-retry.js`), consumido también por `acquireGate` de `delegation-reservations.js` — ver "CI roja en el segundo push a `origin/main`" más abajo para el porqué (un presupuesto de intentos depende de la velocidad de la máquina) y la evidencia medida.
- [x] **0.10** Lock alrededor de observe→relaunch en `executeResume` (`resume.js:25-50`): re-leer el run bajo el lock, verificar que `transportIdentity` no cambió desde `planResume`, rehusar con conflicto si se movió. Hoy dos `resume --yes` concurrentes doble-relanzan al mismo worktree. *(ffc6929)*

### Batch C — Assignment, config y delegación (D1, D8, D10, D11, D13, D14)

- [x] **0.11** Cablear `project.verify` del registry → plan → `buildAssignmentTemplate` y eliminar el fallback hardcodeado (`assignment.js:176-180`; el fallback referencia los tests *de este repo*). Fallback nuevo: instrucción genérica de descubrir y correr los checks propios del proyecto. **Prerequisito de 2.3 (workflow verify).** *(006d179)*
- [x] **0.12** `bin/workflow.js:701`: pasar `{limit: LAUNCH_OUTPUT_LIMIT}` en el emit del execute report, como ya hacen los previews (`:679,:686`). Hoy reportes entre 12k y ~77.5k chars salen como JSON truncado inválido. *(006d179)*
- [x] **0.13** Extender `RAW_CONTROL_ARGUMENTS` de Claude con `--settings`, `--mcp-config`, `--append-system-prompt`, `--session-id`, `--resume` (`registry.js:32-39`). Hoy un profile puede pisar el `--settings` generado que el digest aprobó (`harnesses.js:160-164`, last-wins). *(006d179)*
- [x] **0.14** `reconcile.safeStatus`: devolver `{dirty: null, error}` y que el clasificador trate status desconocido como conflicto (`reconcile.js:65-71`). Hoy un `git status` que falla se reporta como clean y alimenta el flujo de aprobación. *(006d179)*
- [x] **0.15** Requerir claim token por delegación en **toda** generación, no solo remediaciones: mintearlo al claim, pasarlo al child solo por su env privado, exigirlo al recibir el resultado. Un child con bash podía forjar el resultado de un sibling. *(006d179)* — **implementado en `submitDelegationHandoff`** (el borde que cruza el child), no en `recordResult`: así el primitivo del store sigue usable por los llamadores internos de confianza y hay un solo punto de enforcement por caso (remediación vs generación normal).
- [x] **0.16** Reservas de delegación: liberar el lease al aterrizar un resultado terminal + comando `workflow delegation release <run-id> <delegation-id>` para el residuo de start-failures. Una sola delegación writer exitosa brickeaba el lane para siempre. *(006d179)* — **implementado con `releaseForDelegation({projectAlias, delegationId})`** en vez de `release({reservation})`: el ownerToken se mintea dentro de `reserve()` y nunca se persiste fuera del lease, así que ningún llamador posterior puede presentarlo (por eso `release()` no tenía llamadores). La autorización viene de que ambos call sites verifican contra el run store que la delegación ya no corre.

## Fase 2 — Lado de salida: superficie de operador

El lado de entrada (plan→digest→launch) es el moat; acá es donde todo el ecosistema es más fuerte. La gramática de digest existente se reusa tal cual.

- [x] **2.1** `workflow runs [--project X] [--state Y]` — board read-only cross-proyecto: id, estado, ticket, harness, ~~worktree~~ (no existe tal campo — la tabla compacta no lo finge; ver "Dos cosas verificadas" en el cierre de 2.1 abajo), updatedAt desde el state root. **Depende de 0.3** (o el board se brickea con el primer launch crasheado). Hoy no hay forma de responder "¿qué corre, qué necesita input, qué completó sin mergear?". **Primer ítem de Fase 2, y el primero que es feature y no hardening fix.** *(c0c207c..6f8a332)*
- [x] **2.2** `workflow inbox [project] [--format compact|json]` — runs bloqueados en prompts de permiso, agregados cross-proyecto. Ver "2.2 completa" en el cierre de 2.2 abajo para los tres buckets (`blocked`/`waiting`/`unresolved`) y por qué `events.jsonl`, que el roadmap nombraba como fuente, no se usó. *(e70f446..31dbdbb)*
- [x] **2.3** `workflow verify <run-id> [--format compact|json]` — re-ejecutar los comandos verify del proyecto dentro del worktree exacto grabado, evidencia estructurada pass/fail en el event log del run, visible en `workflow result`. **Depende de 0.11.** Hoy "verification: passed" es autorreporte del worker: confianza, no evidencia. *(097f212..9ed059c)*
- [x] **2.4** `workflow merge <run-id> --dry-run` → `--approval-digest` — preview del argv exacto de merge/rebase + conflictos, ejecutar solo con digest. Cierra el último paso sin gobierno del arco. Worktree preservado post-merge (no-cleanup). — **mergea, no rebasea**, y la razón no es de gusto: solo el merge tiene un oráculo de conflictos no mutante. Ver "2.4 completa" abajo. *(aa58593..02f3090)*
- [ ] **2.5** `workflow archive <run-id>` — cierre explícito confirmado, solo para runs terminales con dueño probado muerto/cerrado (**depende de 1.1**): remueve worktree y tab, preserva el state dir. Hoy los runs exitosos acumulan worktrees/tabs/state para siempre.
- [ ] **2.6** Critic advisory post-verify: delegación Pi (lane advisory existente, rol code-reviewer) que revisa el diff contra assignment.md; veredicto como evidencia, jamás canónico. Adoptar severidades `aside|concern|blocker` del patrón advisor de oh-my-pi.

## Fase 4 — Capacidades modernas (opt-in, cada una amerita spec propio)

- [ ] **4.1** Sandbox opcional por profile: `sandbox: bwrap` en projects.yaml que prefija el argv del harness (bubblewrap/sandbox-runtime: worktree + run dir escribibles, home enmascarado, política de red explícita). El argv ya es shell-free y entra al approval digest — el sandbox queda cubierto por la aprobación gratis. Hoy Pi y Claude corren con privilegios plenos del operador.
- [ ] **4.2** Presupuestos: techo de costo por proyecto/launch en projects.yaml; hooks (que ya corren por prompt/stop) comparan costo acumulado vs techo y apéndean evento `budget-exceeded`; `workflow worker status` muestra acumulado vs techo. Quick win incluido: capturar cost/tokens del payload stdin del statusline de Claude (`claude-statusline.mjs:62-66` hoy los descarta) y flippear los capability bits (`telemetry-adapters.js:4-9`). Con modelos clase Fable corriendo días, esto es necesario, no nice-to-have.
- [ ] **4.3** Fan-out: `workflow launch --agent pi-worker,claude-worker` (o `--fan-out N`) — un preview enumerando N runs con nombres sufijados, un digest cubriendo el set, N run records. La maquinaria de aislamiento ya hace seguros los siblings. Bake-off cross-harness = el payoff único del diseño multi-harness. Diseñar merge queue junto con 2.4 cuando esto exista.
- [ ] **4.4** `herdr pane report-agent` con runId como metadata desde los tres hooks (settings Claude, hooks.json Codex, extensión Pi) → correlación pane↔run positiva en session-transport/reconcile; retirar el carve-out `trustPaneWhenSessionUnreported` de Codex (`session-transport.js:44-59`), el único lugar donde "no guessed sessions" se dobla.
- [ ] **4.5** Transporte Pi por RPC upstream (JSONL stdin/stdout, `docs/rpc.md` de pi-mono) en vez de interacción por pane — framing determinista, identidad de sesión exacta gratis para resume/close. Evaluar también `/fork` de session trees para el recovery lane.
- [ ] **4.6** Checkpoint git pre-launch: ref `refs/workflow/<run-id>/pre-launch` en el worktree antes de arrancar el worker, logueado a events.jsonl. Rewind que captura efectos de bash, aditivo (no-cleanup), base de diff exacta para status/reconcile.
- [ ] **4.7** Escala del plano de observación: rotación por tamaño de events.jsonl (post-entrega de notificaciones terminales), split active/archived o índice de runs no-terminales para que los watchers no escaneen O(historia) cada 5s (`delegation-store.js:560-572`). *(D16)*
- [ ] **4.8** `workflow mcp` — servidor MCP read-only por stdio (spec 2026-07-28, core stateless): doctor/plan/status/result/reconcile como tools tipadas; mutaciones NO expuestas; muere con el cliente, sin daemon.
- [ ] **4.9** Telemetría: mapear el vocabulario a `gen_ai.*` (OTel GenAI semconv) + `workflow telemetry export <run-id> --format otlp-json`. Transformación pura de archivos.
- [ ] **4.10** Memoria por repo (patrón mnemopi): consolidar gotchas de runs completados (result.json/events.jsonl) en un banco por proyecto, inyectado en assignments futuros con tope de tokens y redacción de secretos; lease+heartbeat para consolidadores concurrentes. Contenido tratado como untrusted input.
- [ ] **4.11** Disciplinas de durable execution: `workflow reconcile --replay` que reconstruye estado solo desde events.jsonl vía lifecycle.js y asserta equivalencia con run.json; claves de idempotencia en pasos mutantes del launch; eventos de compensación enumerables por reconcile.

### CI roja en el segundo push a `origin/main`

La segunda corrida de CI (`b146e3d`) falló un test — `beginRemediation races claim atomically so only one follow-up child launches` — que había pasado en la primera corrida (`ok 309`) contra código de producción idéntico: la rama anterior a esta era test-only. **No fue flakiness.** La propia aserción del test nombra la propiedad que se rompió:

```js
  // The loser is refused by the claim guard (or by the record having already
  // moved past a remediable state once the winner finished) — never by gate or
  // lock contention, which bounded retries absorb.
  assert.match(rejected.reason.message, /already claimed|allowed state/i);
```

En CI el loser recibió `Reservation project gate is active; manual inspection required` — contención de gate, no el claim guard. El propio comentario de `acquireGate` promete lo mismo que rompió la aserción: los holders concurrentes son de escala de milisegundos, así que un retry acotado debería absorber una colisión viva en vez de mandar al operador a inspeccionar un gate que está por liberarse.

**La falla estaba en la unidad.** Los dos mutex presupuestaban sus reintentos en **intentos** (`maxAttempts = 3` con `sleep(25 + random*75)` — dos sleeps, tolerancia de entre ~50 y 200 ms) mientras la garantía que prometen es sobre **tiempo**. Un presupuesto de intentos depende de la velocidad de la máquina. Medido localmente antes del fix: 15/15 pasa sin carga y 12/12 con 36 workers quemando CPU — y aun así falló en un runner de dos núcleos.

**El fix:** un único retry acotado por tiempo, compartido (`src/workflow/bounded-retry.js`), consumido por `acquireLockWithRetry` de `run-store.js` y por `acquireGate` de `delegation-reservations.js`. Es además la **quinta** copia de la misma lógica en este repo, después del argv de `ps` (1.1b, 1.1c), los invariantes de delegación y la coreografía de remoción de mutex (1.4), y el protocolo de lifecycle (1.2).

**Lo que no cambió:** el residuo genuino de un crash sigue terminando en el mismo error de inspección manual — solo se alargó la espera antes de declararlo. Un lock de run **stale** sigue fallando rápido hacia el flujo de recuperación de `workflow unlock`, en vez de esperar el presupuesto.

**Esto reduce, no cierra, la exposición que anotó 1.2.** Esa entrada registró que, bajo contención del lock, perder la escritura del marker puede saltear en silencio un incremento de generación (ver el bullet de `acquireLockWithRetry` en "1.2 completa" arriba) — anotado ahí como riesgo aceptado, no corregido. Un presupuesto de reintento más ancho reduce la ventana en la que esa pérdida puede ocurrir; no la elimina.

**Costo honesto:** dos tests existentes que ejercitan residuo genuino ahora tardan el presupuesto completo (~2s cada uno) antes de llegar al error de inspección manual, porque eso es exactamente lo que significa el presupuesto — antes tardaban ~200ms. Y un test existente tuvo que cambiar: pinneaba el contrato viejo de conteo de intentos asertando el número de sleeps (`sleeps.length === 2`), así que ahora conduce un reloj falso a través del mismo seam de `sleep` inyectado en vez de eso.

**2.4 completa — cuarto ítem de Fase 2, y el último paso del arco que estaba sin gobierno.** `workflow merge <run-id> --dry-run` previsualiza, por cada repositorio que el run grabó, el argv exacto y shell-free de `git merge --no-ff --no-edit <rama>` junto con los conflictos que ese merge produciría, calculados sin tocar ningún working tree, índice ni ref; `workflow merge <run-id> --yes --approval-digest <digest>` ejecuta, y solo contra el digest que esa preview imprimió. Es el mismo sobre preview → digest → execute que `launch` pone alrededor de arrancar un worker. Deliberadamente sin prompt y/N: un prompt aprueba un renderizado, un digest aprueba los commits exactos, y merge es el comando donde esa diferencia es todo el punto. El merge corre en el **base checkout** del proyecto, no en el worktree del run — `base_branch` es lo que tiene que avanzar, y git además prohíbe checkoutear una rama que ya está checkouteada en otro worktree, así que la alternativa no existe ni en principio. El worktree del run no se toca: ni la rama, ni el HEAD, ni un byte de su working tree.

**Dos premisas heredadas, corregidas antes de diseñar nada encima.** Es otra instancia de la lección que este documento ya tiene registrada sobre verificar toda premisa heredada contra el código, y las dos habrían torcido el diseño.

La primera: **`src/workflow/git.js` nunca fue read-only.** `createWorktree` (`git.js:311`) corre `git worktree add <path> <branch>` o `git worktree add -b <branch> <path> <base>` — la segunda forma **crea una rama** — y se llega desde producción en `execute.js:986`, dentro de `executeStart`. El control plane viene escribiendo en repositorios reales del operador desde que existe el lane de launch.

La segunda, que es la que importa: **2.4 no es la primera escritura git del arco; es la primera escritura a una rama compartida y ya checkouteada.** `git worktree add` es puramente aditivo y aislado — un directorio nuevo, un ref nuevo, nada existente se toca, ningún otro checkout de ese repositorio se ve afectado. `git merge` dentro de `base_branch` avanza una rama compartida sobre la que el checkout propio del operador probablemente está parado, y eso es un acto categóricamente distinto. **Esa distinción, y no el absoluto falso, es lo que justifica poner un digest adelante.**

**El hallazgo de datos reales que le dio forma al comando.** `run.repositories[].branch` es una **intención de tiempo de launch**, no un hecho sobre dónde está el trabajo. El run real `0b2612a8` (`completed`, tres repositorios) graba `feature/1216110941098331/registro-impl`: ese ref no existe, y el worktree del path grabado está en `feature/registro-impl`, en un commit que `dev` todavía no contiene. Dos de los ocho runs reales de esta máquina están en esa forma. Un merge manejado desde el registro fallaría contra un ref inexistente en el mejor caso e integraría una rama vieja en el peor. Así que el source se resuelve desde el **HEAD del worktree** — rama y sha — y el desacuerdo con el registro se **nombra prominentemente en la preview y entra al digest**: ni sustituido en silencio, ni tratado como conflicto bloqueante. Bloquearlo dejaría el comando inservible contra *todos* los runs multi-repositorio completados que hoy existen de verdad, y el desacuerdo es información que el operador debería aprobar sabiendo, no una razón para rehusar. El digest ata los **shas** resueltos, source y base, no solo nombres de rama.

**Las dos decisiones abiertas, resueltas, con su razonamiento.**

**Mergea, no rebasea**, y la razón de más peso no es de gusto: **solo el merge tiene un oráculo de conflictos no mutante.** `git merge-tree --write-tree` (git ≥ 2.38; medido contra 2.43 acá) corre la maquinaria real de merge — contenido a tres vías, detección de renames, conflictos directorio/archivo, consolidación recursiva de ancestros — y reporta los paths conflictuados exactos sin leer ni escribir working tree ni índice. Para rebase no hay equivalente: predecir un rebase es replayear cada commit, lo que requiere estado real (un worktree scratch y un `git rebase` de verdad que después se aborta), y una preview que no puede predecir no es una preview. Segundo, **un rebase reescribe el artefacto del propio run**: la historia de la rama que ese worktree tiene checkouteada, y que puede estar ya pusheada — preservar el directorio mientras se reescribe la historia a la que apunta preserva la mitad equivocada. Un `--rebase` futuro no queda prohibido por nada de acá; simplemente no es diseñable hoy al mismo estándar, y shipearlo a uno más bajo haría desparejo el gobierno justo en el comando cuyo propósito entero es gobernar.

**La evidencia de verificación entra al digest y no gatea.** El spec de 2.3 dejó esto explícitamente diferido acá. Las dos puntas del dilema son reales — gatear hace que la evidencia importe; no gatear mantiene el comando usable en un proyecto sin comandos `verify` — y ninguna de las dos es el diseño: un gate duro necesita un escape hatch (`--force`) apenas un proyecto no tiene comandos verify o un operador tiene una razón legítima para integrar una rama roja, y un escape hatch en el único paso gobernado es un agujero de gobierno con un flag puesto. En cambio, la última evidencia se lee en la preview y se pliega al payload del digest: aprobar un merge es aprobar el merge *de estos commits, con este estado de verificación*. Se re-corre `workflow verify` o se pushea otro commit, cambia el digest, y la aprobación anterior queda stale contra la maquinaria que ya existía — verificado punta a punta contra el CLI real, donde correr `verify` movió tanto la línea de la preview como el digest. **El límite honesto, dicho sin vueltas:** un operador que nunca corrió `workflow verify` recibe `verification: none` en su preview y en su digest, **y puede aprobar eso**. El control plane expone; el operador decide. Lo que no hace es dejar aprobar una cosa y mergear otra. El `state` propio del run se trata igual — expuesto, digerido, nunca gateado; de los ocho runs reales, dos están en `manual-handoff-required`, y un worker que paró para pedirle algo a un humano no carga por eso trabajo que no se pueda mergear.

**Lo que no hace.** No pushea: publicar a un remoto es un acto hacia afuera con su propia pregunta de aprobación, y la integración local es una unidad de trabajo completa. No limpia nada — worktree, rama y tab de Herdr sobreviven intactos; la remoción es del ítem **2.5**. No rebasea. No resuelve conflictos: un conflicto predicho se reporta y se rehúsa, resolverlo es trabajo del operador en su propio checkout. Y **no es atómico entre repositorios**, y lo dice — ver el pendiente correspondiente arriba.

**Lo que encontró correrlo de verdad y la review adversarial, que es el tema más consistente de este roadmap.** Tres tareas subagent-driven más este cierre, y cuatro rondas de fix: una en la tarea 1, una en la tarea 2, dos en la tarea 3.

- **Exit 1 de `merge-tree` no significa "conflicto".** Medido: un ref que git no puede mergear sale con **1 y stdout vacío**, indistinguible de un conflicto por exit code solo. El mapeo literal del brief (`exit 1 → conflicted`) habría reportado `status: "conflicted", conflicts: []` — "el merge conflictúa, en cero archivos", equivocado en las dos direcciones y que además se imprime como una tabla de conflictos vacía. Resuelto fail-closed: exit 1 **sin tree OID** es `unknown` con la razón, que carga el stderr propio de git. `unknown` bloquea igual que `conflicted`, así que lo que cambia no es la seguridad sino que al operador se le dice que el oráculo no pudo correr en vez de mostrarle una lista vacía. De la misma familia, encontrado en la primera review: `String(undefined)` es el string truthy `"undefined"`, así que un runner que contestaba `{code: 0}` sin stdout producía `status: "clean"` — un falso verde en la función cuyo mandato entero es fallar cerrado. Ahora el primer campo se valida contra un object id sha1 o sha256 real, escrito como dos alternaciones y no como `{40,64}` para que un string de 47 caracteres no pase.

- **El hueco de namespace de refs del base checkout, el más filoso de los técnicos.** `refExists` prueba que un **objeto** está presente; `git merge <branch>` resuelve un **nombre**, en el namespace de refs del propio base checkout. Son preguntas distintas y solo la segunda es la que importa: el digest ataba un sha, pero el `git merge <branch>` ejecutado resuelve el nombre localmente, así que un clon aparte con una rama local vieja del mismo nombre habría mergeado un commit distinto del previsualizado. Cerrado con un primitivo nuevo `resolveRef` (nunca tira; ausente, ambiguo o no-commit contesta `null`, que el llamador trata como refusal) y tres refusals distintas donde había una. Un `reason` de merge no es una oración que escriba este código: es el stderr propio de git, y git escribe varias líneas. Renderizado crudo, la segunda línea aterrizó en `Reasons:` **sin etiqueta de repositorio adelante**, y en ese caso exacto la línea huérfana era el consejo de git para *completar* el merge, sentado sin atribución dentro de un reporte sobre un merge que falló. Corregido indentando las continuaciones cuatro espacios y preservando el texto de git verbatim en vez de colapsarlo a una línea, con test de regresión que nombra dónde se encontró.
